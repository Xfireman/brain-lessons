# 用你自己的项目试一条规则

这次试用只回答一个问题：它有没有让一条反复纠正的项目规矩更容易维护？
先选一个小型、无敏感内容的本地项目，保留原有权限和沙箱设置。

1. 按 [README](../README.zh-CN.md#在实际项目中使用) 安装 Codex hook 和
   `brain-remember` 技能，在 `/hooks` 中审阅并信任这条 hook。
2. 选一个实际反复出现的命令或路径问题。用自己项目的路径，不要原样照搬演示。
3. 对 `$brain-remember` 说这条纠正，先要候选规则、一个命中例子和一个邻近的允许例子。
   范围看清楚后让它保存。需要阻止时明确说“拦截”，否则先用提醒。
4. 让 Codex 展示 `check` 和两次 `recall` 结果。不要为了测试真的执行危险命令。
   实际宿主拦截可以用无害的生成文件样例；[离线演示](demo.md)不需要授予 hook 信任。
5. 照常工作。一周后决定保留、调整还是移除。觉得没有必要，也是一条有用反馈。

## 反馈什么

在仓库创建 **Trial feedback** issue，只写合成或脱敏的内容：

- 系统、Codex 界面和版本、Brain Lessons 版本。
- 第一个卡点：安装、信任、选规则，还是匹配范围。
- 用一句话描述纠正，附最小命中例子和允许例子。
- 实际工作中帮到过什么，有没有误拦，还是完全没有触发。
- 一周后：继续使用、调整了，还是卸载了，以及原因。

不上传真实会话、密钥、内部路径或公司代码。产品没有遥测，维护者只能通过你主动提供的反馈了解使用情况。
下载量、克隆量和测试通过都不能证明有人持续使用。

## 撤销

在项目中运行 `brain-lessons uninstall codex --with-skill`，保留教训和其他配置。
如果手工修改过技能，安装器会停止并保留修改。也可以只运行
`brain-lessons uninstall codex` 移除 hook，保留技能用于手动编写规则。

停用单条规则，将对应 JSON 的 `enabled` 改成 `false`。
